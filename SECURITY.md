# Security Policy — Aikya Harness

Security is a core requirement of Aikya Harness. The project provides an
AI-assisted engineering environment for software development, infrastructure
as code and DevOps with explicit human approval for risky operations.

We welcome responsible vulnerability reports affecting the harness or users.

## 1. Supported versions

| Version or branch | Policy |
|---|---|
| Latest published stable release | Priority security support |
| develop | Development fixes; no stability guarantee |
| Older releases | Case-by-case assessment |

Older releases may stop receiving security fixes. Review repository releases
and advisories to confirm support.

## 2. Reporting a vulnerability

**Do not publish security vulnerabilities in public issues.**

Prefer GitHub's private **Report a vulnerability** flow when enabled.
Provide affected version/commit, environment, affected component, impact,
reproduction conditions, evidence and proposed mitigation if available.
Sanitize tokens, secrets, personal data, production logs and access details.

If private reporting is unavailable, use the maintainers' verified private
contact channel. Do not assume an unpublished email address exists.

## 3. Vulnerability handling

Maintainers assess scope and impact, reproduce safely where possible,
determine affected versions, create a targeted fix, add regression tests and
coordinate disclosure. Response and release timing depend on severity,
exploitability, maintainership availability and validation requirements.

## 4. Areas of special concern

### Command execution
The harness must not execute arbitrary untrusted shell commands, destructive
Git operations, unauthorized SDK installers, remote deployments, or production
infrastructure changes. Approval for a plan does not authorize its execution.

### AI agents and Agent Skills
Agent definitions, tool allowlists, delegated permissions and external skill
provenance must be reviewed. A natural-language instruction alone is not a
security boundary. Read-only reviewers should not need mutating tools.

### Filesystem safety
Protect customized files, symlinks, project-relative paths and user-owned
documents. Keep secrets out of generated sources and reports. Use bounded,
reviewable writes; avoid traversal outside the intended workspace.

### Infrastructure and DevOps
Terraform, OpenTofu, Ansible, Docker, Kubernetes, Helm and CI credentials
require separate authorization and least privilege. Manifest files do not
prove that infrastructure was deployed or verified.

### Supply chain
Review external repositories, licenses, pinned versions and checksums before
installation. Never run unreviewed third-party code from startup hooks.

## 5. Responsible investigation
Use only authorized, non-destructive verification and disclose findings
privately. Avoid accessing third-party systems, real credentials or customer
data. Document unknowns rather than inferring a clean security posture.

## 6. Security principles
- Least privilege and explicit approval for sensitive operations.
- Clear separation of read-only analysis, local implementation and remote
  operations.
- Safe default model routing and no unapproved auxiliary model activation.
- Privacy-aware logs and bounded context extraction.
- Deterministic tests and evidence-based reporting.
- Backward compatibility without overriding user customization.

## 7. Third-party components
Upstream vulnerabilities must be assessed for actual applicability to Aikya
and reported to the original project where appropriate.

## 8. Disclosure
A security advisory may describe the issue, affected versions, impact,
mitigations, fixed release and recommended upgrades after a reasonable
mitigation exists. Avoid publishing unnecessary exploit details prematurely.

## 9. Limits
Generated configurations and checks do not guarantee system security.
Users remain responsible for validating permissions, dependencies, credentials,
deployment and operational controls before real-world execution.
