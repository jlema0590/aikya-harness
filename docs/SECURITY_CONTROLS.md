# Security and source-quality controls

## Enforced by the optional task controller

- Explicit authorization and dependency-ready ODD/SDD task approvals before execution.
- An allowlist of editable files. Model tools are Read/Edit/Write for implementation
  and Read for review/extraction; shell, agents and MCP tools are not exposed.
- Contained regular paths; symlinks, traversal, common secret paths and model writes
  into Aikya control files or CLAUDE.md are rejected.
- Settings/hooks need review; changed approval, context and settings fingerprints
  block continuation. A copied checkout cannot inherit loop authorization.
- Bounded turns, time, iterations and reported estimated cost, with cancellation and
  conservative handling of interrupted effects or unknown usage.
- Actual configured Validate and Security processes plus read-only model Review.
  A successful model response alone cannot complete a task. Later candidate changes
  invalidate checks. The controller records command and candidate fingerprints.
- The source-quality gate blocks oversized candidate files and Python syntax errors.
  Source-size exceptions live in a protected control path and are fingerprint-bound.

Configured check processes execute their reviewed argv without an implicit shell.
They still run with the developer's operating-system permissions: an explicitly
configured interpreter, script or hook can execute arbitrary code. A zero exit code
only proves that the configured check passed, not that it is a sufficient scanner.

## Normal interactive workflow

Template permissions deny reads of common .env paths and ask about publication or
infrastructure changes. guard_bash.py rejects selected destructive command patterns.
check_edit.py supplies syntax/quality feedback after Edit/Write. Instructions and
patterns help the developer but are not an operating-system sandbox; variants of a
command, custom settings or another editing tool require independent controls.
Existing owner-controlled settings and CLAUDE.md are preserved during adoption.

Configure stack-appropriate tests, linters, dependency/vulnerability checks, secret
scanning and infrastructure validation in harness.json or CI. Aikya does not silently
install or certify those tools. Missing checks remain NOT VERIFIED. Code review must
assess authentication, authorization, injection, data handling and relevant threats.

## Maintainability is a separate gate

Changed source files above 1,000 physical lines must be split by responsibility or
have an explicit reason and current SHA-256 in .aikya/code-quality-exceptions.json:

```json
{
  "schema": 1,
  "exceptions": [
    {
      "path": "src/generated_protocol.py",
      "sha256": "REPLACE_WITH_CURRENT_64_CHARACTER_SHA256",
      "reason": "Generated protocol output; change the generator rather than hand-splitting it."
    }
  ]
}
```

The placeholder is not an accepted hash. A subsequent source edit invalidates the
exception. Python functions above 100 lines and repeated nontrivial AST bodies are
warnings for review, not an automatic rewrite or proof of a vulnerability. The
checker handles source-file size for listed languages; clone analysis is Python
only. Third-party/vendor data and generated documentation are excluded from --all.
Explicitly supplied source paths are still checked.

To enforce this in a normal project's configured checks, use a required check with
argv equivalent to python aikya/scripts/harness/code_quality.py --changed --base HEAD.
Choose the correct comparison base for CI; --all is useful for a historical audit.

## Data and durability

Authoritative Markdown and loop checkpoints share fsync plus atomic replacement;
this is per-file durability, not a multi-file transaction or signed evidence.
The presentation cache stays disposable. Private memory uses external directories,
restricted POSIX modes, explicit retrieval and reviewed identity migration. It is
not encrypted. Model extraction requires separate opt-in and produces pending notes.

Real provider acceptance is performed separately in the user's chosen environment.
Local subprocess and SDK-option tests do not prove behavior of a live model session.
