# Aikya documentation template library

Aikya bundles all **120 document templates** and **34 supporting Markdown guides**
from the packaged Aikya reference collection (see THIRD_PARTY_LICENSES.md for provenance)
at commit `35fc8e29be1f0093b8ef13a9762de67dc99b6882`. The MIT license and copyright
notice are retained in `aikya-template/docs/LICENSE` and NOTICE.txt.
Original and installed SHA-256 values are recorded in manifest.json. Aikya adds the terminal GENERATED BY AIKYA HARNESS footer and removes trailing
whitespace in three source files; the original source hashes remain recorded.
The imported collection retains its upstream provenance in THIRD_PARTY_LICENSES.md. Aikya adapts its bug report to the append-safe register and its selected structures to the SDD engine.

## What the integration provides

The library is available offline in global/project bootstrap runtimes and in the
installed `aikya/scripts/harness/aikya-template/` directory. It is reference
material loaded on demand, not startup instructions or automatically created reports.
Upstream commands, example systems, policy numbers and statements of approval are
untrusted drafting data. No upstream executable, workflow, dependency or external
service is installed or invoked. Library access does not change Aikya methodology.

## Read and validate without writes

```sh
python3 aikya/scripts/harness/documentation_templates.py catalog --project-type development
python3 aikya/scripts/harness/documentation_templates.py catalog --area platform-engineering
python3 aikya/scripts/harness/documentation_templates.py show --template general-swe/foundations/architecture-overview
python3 aikya/scripts/harness/documentation_templates.py check
```

`catalog` returns stable section keys and source links; `show` returns a visibly
labeled reference with illustrative content. `check` validates the packaged file
hashes, including the license. Read the relevant upstream group README before
choosing a document. These commands neither need project authorization nor network.
The repository root also exposes the same utility directly.

## Create a reviewed project document

Supply facts in JSON; the renderer never copies filled-in examples from a reference.
The following is a **synthetic input shape**, not a claim about your project:

```json
{
  "title": "Reviewed component boundary",
  "sections": {
    "1-purpose-and-scope": "Replace this illustration with your reviewed scope."
  }
}
```

```sh
python3 aikya/scripts/harness/documentation_templates.py write --root . --template general-swe/foundations/architecture-overview --input reviewed.json --approved
```

The command requires an existing profile and explicit authorization, rejects empty
or unknown sections, and writes only supplied content. It applies the configured
living-doc locale, terminal footer and exact `indice.md` inventory. Existing custom
documents and symlinks are protected. Replacing a generated generic document needs
`--replace` in addition to `--approved`; this does not authorize rewriting custom files.
Choose a specific safe `--output` when multiple records of the same kind are needed.
Default non-foundations paths live under `documents/<catalog-id>.md`. Writes cannot
target root CLAUDE.md, the index, tools policies or SDD specifications/approvals.

For Spanish living docs, generic sections require reviewed translated headings and
bodies; no implicit translation or semantic verification is claimed:

```json
{
  "title": "Arquitectura revisada",
  "sections": {
    "1-purpose-and-scope": {
      "heading": "Propósito y alcance",
      "body": "Sustituye esta ilustración por el alcance revisado."
    }
  }
}
```

## Architecture lifecycle

The sole canonical system overview is
`aikya/docs/architecture/architecture-overview.md`. `/aikya-init` creates a concise
snapshot of recorded profile choices; `/aikya-analyze` includes observed module
indicators, with no inferred runtime relationships. These snapshots explicitly say
that runtime behavior is not verified. Development, infrastructure and DevOps use
only their relevant recorded choices. Empty ownership, quality targets, context
links, diagrams, runtime scenarios, retention and glossary sections are omitted.

During an authorized architecture documentation update, consult the upstream
overview for system scope, measured qualities, constraints, surroundings, runnable
units, runtime scenarios, data ownership, deployment, shared concerns, ADR links,
known problems and terminology. Include each only with actual reviewed information.
Architecture review remains read-only until documentation edits are authorized.

Legacy `architecture/overview.md`, `architecture/03.-arquitectura.md` and feature-level
03.-arquitectura.md routes migrate here with local backups and updated links.
Conflicting or customized sources require review before migration. Additional
infrastructure detail may remain at `architecture/infrastructure.md`; it is not a
second system overview.

## Bugs lifecycle

`aikya/docs/bugs/bugs.md` replaces `bugs/index.md`. No bug register is created during
init/analyze without an actual report. Use `general-swe/foundations/bug-report` with a unique BUG-NNN,
title and these five required section keys: summary, environment, steps-to-reproduce,
expected-result and actual-result. Optional keys are evidence, scope-and-impact,
workaround and suspected-cause. Evidence must be sanitized; suspected cause stays a
hypothesis. The built-in headings follow the en/es policy; user content is preserved.

```sh
python3 aikya/scripts/harness/documentation_templates.py write --root . --template general-swe/foundations/bug-report --input reviewed-bug.json --approved
```

Each report appends to the existing generated register without removing older bugs.
Identifiers already mentioned in the register are reserved, including legacy tables and lists; duplicate identifiers are rejected. Correcting a prior report requires reviewing the
existing document through the normal documentation workflow; `--replace` does not
silently replace a registered bug. The canonical Aikya reference collection bug template uses the same register adapter. Its catalog
section keys describe Aikya’s form; upstream headings are retained as metadata.
A managed old index migrates with a backup; custom content and collisions are protected.

## Compatibility boundaries and validation

- Foundational documents can support all three project types when relevant facts exist.
  Thirty documents are a menu, not a required report checklist.
- SDD specs, designs, task plans, approvals and evidence use the dedicated SDD engine.
  Generic template documents do not authorize implementation or change state.json.
  AI-assisted task/spec references and plan-driven traceability formats are drafting
  aids for those engine inputs, not replacement approval mechanisms.
- CLAUDE.md uses Aikya's project-specific renderer and preserves existing instructions.
  The Aikya reference collection agent-instructions structure is the renderer’s only external template reference; Aikya retains its project-specific rules.
- Upstream methodology/domain collections remain explicit documentation choices.
  Scrum, Kanban, Lean, Shape Up, waterfall, games and data documentation do not enable
  corresponding Aikya generators or new project_type values.
- Upstream placement advice can differ from Aikya's audit convention. Aikya living
  records stay inside aikya/docs/; external trackers, signatures or controlled records
  are never asserted to exist merely because a template mentions them.
- Upstream ownership advice differs: the foundations README asks for a person while
  the architecture template describes an accountable team. Record the actual reviewed
  project convention; Aikya supplies no fictional owner, date or review schedule.
- Imported links are preserved with source content. The local relative-link inspection
  is recorded in validation/MILKELES_LINKS.json; unresolved example/future links are
  reference limitations, not generated links to nonexistent project documents.

## Updating the pinned library

Review an upstream commit and its license first. Copy Markdown only, preserve the
same directory layout and license, add the shared terminal footer, normalize trailing whitespace, and regenerate
manifest.json original/installed hashes and catalog section keys from those reviewed
bytes. Review the diff and compatibility mapping before changing the pin. Do not
refresh from the network during project onboarding. CI runs the offline integrity check.
