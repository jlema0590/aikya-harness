# Maintainable source changes

Inspect existing modules and helpers before introducing another implementation.
Keep one authoritative implementation; packaging copies and historical fixtures
must have an explicit purpose. Do not add another runtime or memory engine to
implement a feature already supported by the harness.

Changed source files must contain at most 1,000 physical lines. Split by cohesive
responsibility with explicit interfaces; do not compress statements or move an
unrelated block merely to satisfy a counter. If decomposition exceeds the approved
task files, request a scope adjustment. Never silently refactor an existing project.

Run the installed `code_quality.py` against the changed source files. Python
functions above 100 physical lines and repeated nontrivial Python AST bodies are
review warnings; use engineering judgment and tests before extracting helpers.
Other languages receive the source-file size check, not a semantic clone analysis.

An exceptional large file requires `.aikya/code-quality-exceptions.json` with
schema 1 and an exceptions array. Each item needs path, the current sha256 and a
specific review rationale of 20–1,000 characters. A subsequent edit invalidates the
exception. These are owner-reviewed local decisions, not signed approvals.

The optional task loop blocks completion on quality errors. Normal Edit/Write
hooks provide feedback after a write; configure the checker as a required project
or CI check to enforce it outside that loop. Maintainability checks do not replace
tests, dependency review, secrets scanning or project-specific security analysis.
