# Mandatory living documentation policy

Read aikya/docs/README.md and the relevant feature, architecture or operational
documentation before material changes. When modifying source code, tests,
infrastructure, contracts, security or architecture, update affected pages
under aikya/docs/ and create a traceable REQ-*.md entry for the active request.

- Features: update the actual aikya/docs/features/<slug>/spec.md and relevant roadmap entries when justified.
- Bugs: record reproduction, cause and regression under aikya/docs/bugs/bugs.md.
- Security: update actual controls and findings under aikya/docs/security/security.md.
- Architecture: update architecture/architecture-overview.md and reviewed ADRs when justified.
- Infrastructure/CI: update operations/deployment.md and observability.md.
- Tests: update plan/testing.md with actual check results and pending work.
- Skills: update aikya/docs/skills.md after installation, with verified provenance.

## Language boundary
Read the chosen en/es language from .aikya/docs-policy.json. ONLY markdown files
within aikya/docs/ may use Spanish. All instructions, code comments, logs, hooks,
configs, other documentation and public GitHub files remain English.

For English change records use headings: Changes, Evidence, Updated documents.
For Spanish change records use: Cambios, Evidencias, Documentos actualizados.
Existing Spanish historical records remain compatible with the documentation gate.

Read-only consultations do not require artificial documentation modifications.
Do not record full user prompts, secret values or private data. Execute the
configured docs guard and report failures, never silently bypass requirements.

## Generated document layout

Use lowercase feature folders under aikya/docs/features/. The shared
architecture-overview.md belongs in aikya/docs/architecture/ for init and analyze.
Keep initialization guidance in overview.md and test plans in plan/testing.md.
The tools/ folder contains only agents.md, token-policy.md and, after explicitly
requested external installation, skill-comparison.md. Do not create an empty
comparison, design document, feature record or unsupported analysis report.
Every Markdown document generated by Aikya must end with the exact line
GENERATED BY AIKYA HARNESS, including reports, README files, instructions, skills
and agents outside aikya/docs/. Keep YAML frontmatter first; add the footer once. Use the installed
python3 aikya/scripts/harness/docs_layout.py writer for approved writes, then
refresh indice.md with its index action before running docs_guard. The index
lists the actual Markdown files, including newly recorded REQ documents.

## Canonical records

Keep all Aikya plans, bugs and features inside aikya/docs/: plan/, bugs/ and
features/ respectively. SDD plans stay inside their authoritative specs dossier.
Do not create root plans/, bugs/ or features/ directories for Aikya records.
Use the shared documentation writer and refresh indice.md. Existing project-owned
documents remain owner-controlled; do not move or delete them automatically.
