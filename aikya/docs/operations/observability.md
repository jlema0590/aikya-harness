# Execution and token observability

Aikya records execution metadata and local process outcomes separately from model
usage and provider quotas. The task receipt in `aikya.quality.efficiency` reads only
explicit transcript files. It reports input, output, cache creation and cache reads,
deduplicates cumulative message snapshots and labels time-window attribution.
A time interval is not exact command billing. Unmeasured commands retain null
model/token fields; the canonical coverage table has 28 Harness commands.

`command_acceptance.py` measures stdout/stderr bytes and elapsed process time.
These local measurements do not imply model requests or tokenizer counts. Receipts
retain hashes and aggregates instead of source, prompts or conversation contents.
Account five-hour/seven-day percentages require fresh provider data and valid reset
times. They cannot be reconstructed from the token sum or reset through compaction.

The prompt hook retrieves a bounded current-source packet for implementation
commands. Known invocation IDs prevent duplicate delivery; a native PostCompact
epoch permits fresh delivery on continuation. Unknown identity never uses a timed
seen-cache as proof that context was already delivered. The compacted conversation
text is not copied into the continuity record. Pending checks and budgets remain
in their authoritative stores.

The 75% working-context warning accepts only fresh effective-window telemetry.
Native model-window percentage alone is insufficient. The standard runtime payload
currently leaves the effective working window unavailable; a configured project
window is a request, not observed proof that managed/environment settings applied it.
