# Generated Runtime Adapters and Clean Cross-Platform Installation Plan

> **For Aikya contributors:** Execute the reviewed plan through the native Aikya workflow. Preserve user authorization, installed compatibility contracts and observed evidence. Each task has its own test and commit boundary.

**Goal:** Generate compatibility adapters only for installed runtimes, migrate repository consumers to the package, remove the obsolete root launchers, and deliver clean versioned installation of `aikya-harness` on Windows, Linux and macOS without a repository clone.

**Architecture:** Keep `src/aikya/` as the implementation source. Use one deterministic renderer and the existing `module_map.json` to produce installed adapters through the shared runtime asset inventory. Preserve installed filenames, module alias identity, entry context and upgrade safeguards; build distributions from canonical package resources rather than copying root launchers. Publish a tested wheel and platform entry scripts; keep download, environment and ownership logic in one standard-library bootstrap package, also built into a standalone zipapp for machines where Aikya is not installed.

**Stack:** Python 3.10–3.13, standard library (`venv`, `hashlib`, `zipapp`), existing setuptools build, POSIX shell, Windows PowerShell 5.1+/PowerShell 7, unittest and current offline acceptance tools. The base installation introduces no third-party runtime dependency or model call.

**Specification:** [Verified root-entrypoint analysis](../research/2026-10-24-root-entrypoints.md) and [inventory](../research/2026-10-24-root-entrypoints-inventory.json), captured from develop commit `d37f090918fe0ec6d97787170b784108759bd70a`. Work branch: `refactor/root-entrypoints-cleanup`. This document is a proposal, not an execution receipt.

## Global constraints

- Preserve the 27 public slash commands, ODD/SDD gates, configured locales, permissions, memory behavior and execution phases.
- Preserve installed paths under the shared global runtime, `.aikya/runtime/` and `aikya/scripts/harness/`. Existing hook commands must keep working without rewriting custom settings.
- Preserve the existing per-target adapter selection, including the ODD exclusion of the SDD entry point. Mapping presence alone does not authorize installing an adapter everywhere.
- Keep source data, reference templates, predecessor signatures, frozen fixtures and historical generated-gallery checksums unchanged unless a specific new receipt records an intentional change.
- Preserve explicit `InstallerContext` source/template roots and facade overrides. An incomplete explicitly supplied source must fail, not silently fall back to a different installed package.
- Keep rollback, ownership hashes, exact-content recognition, custom-asset rejection, symlink protection, stale-preview detection and read-only dry runs.
- New plans/reports live under `aikya/docs/`; authored Markdown ends once with `GENERATED BY AIKYA HARNESS`; refresh `indice.md`.
- Implement installer scripts and release-workflow support, but do not bump versions, publish tags/releases, install external skills or invoke live models merely to execute this plan. Future publication follows the reviewed release contract on main; existing releases are not rewritten.
- End-user installation requires neither Git nor a checkout, build backend, administrator privileges, shell activation, a PyPI account or the optional Claude Agent SDK. Require an existing compatible Python with working `venv`/pip; report missing prerequisites without silently installing Python or changing operating-system package managers.
- Keep application installation per user for both registration scopes. `global` means the user’s Claude configuration, never a machine-wide Python installation. `project` requires an explicit existing target directory.
- Cross-platform installation must not weaken security-hook failure behavior or overwrite custom settings. Preserve legacy commands where still valid; render new managed hooks for the actual interpreter and supported host shell.
- Never move a created virtual environment to a different path. Build each version environment at its final absolute location and activate it only after validation.
- `setup.py` remains root build infrastructure. Final root Python inventory is one file, `setup.py`; implementation code remains in the package.

## Compatibility decision

Installed compatibility remains supported: for example, `.aikya/runtime/aikya_session.py` must still load the adjacent packaged session implementation from any working directory. Generated adapters are outputs in target runtimes; they are not checked-in root source files or duplicate prebuilt wheel resources.

Source-root compatibility is intentionally retired after consumers migrate. Commands such as `python3 install.py` and uninstalled `import aikya_session` cannot continue unchanged after those files disappear. Document their replacements and test installed legacy aliases separately. Do not add global import aliases, a meta-path importer or test-only `sys.path` tricks to conceal this interface change.

The contributor development path becomes an installed local package: create a virtual environment, install the existing build prerequisites, then use `python -m pip install --no-build-isolation --no-deps -e .`. Existing console scripts `aikya` and `aikya-setup` and canonical package imports serve repository consumers. Use explicit modules only where a real CLI exists; not every mapped module implements a command-line interface.

## Clean installation contract added to this plan

The verified release workflow currently publishes a source ZIP and `SHA256SUMS`; it does not publish a wheel or installers. The new installation path must first add these release artifacts. Do not document `pip install aikya-harness` from PyPI as available without a separately verified publication contract.

| Platform | Published entry script | Per-user application root | Prerequisites |
| --- | --- | --- | --- |
| Windows | `install.ps1` | `%LOCALAPPDATA%\Aikya` | PowerShell 5.1+ or 7; working Python 3.10–3.13 with `venv`/pip |
| Linux, distribution-independent | `install.sh` with Linux detection | `${XDG_DATA_HOME:-$HOME/.local/share}/aikya` | POSIX shell; HTTPS downloader (`curl` or `wget`); working Python 3.10–3.13 with `venv`/pip |
| macOS | The same `install.sh`, with Darwin detection | `~/Library/Application Support/Aikya` | POSIX shell; HTTPS downloader; working Python 3.10–3.13 with `venv`/pip |

“Universal Linux” means no dependency on apt, dnf, apk, systemd or a specific distribution. It does not promise operation without Python, on every CPU/OS combination, or under an incompatible Claude runtime. Test the supported combinations and publish that boundary. WSL uses the Linux installer; native Windows has its own acceptance gate. Python is not bundled in this first delivery.

Both scripts are thin entry points to the same bootstrap zipapp. Source templates live under `scripts/install/`; CI renders version-pinned scripts under `dist/`. Each published script embeds its release version and bootstrap SHA-256. Download a script from the selected release, inspect it and execute the local file; documentation must not imply that these assets already exist in v7.0.0. Example future invocations after downloading that release’s files:

```sh
# Linux and macOS: register for this user's Claude projects
sh ./install.sh --scope global
# Register only an explicitly selected existing project
sh ./install.sh --scope project --target /absolute/path/to/project
```

```powershell
# Native Windows
.\install.ps1 -Scope global
.\install.ps1 -Scope project -Target 'C:\work\project'
```

`global` registers the existing user-level runtime/skills/settings; `project` registers `.aikya/runtime/` and project-local Claude configuration. Package storage is isolated under the application root in either case. Installation registers Aikya; it does not choose ODD/SDD, initialize business documents or call a model. `/aikya-init` and `/aikya-analyze` keep their existing methodology choices.

Use `versions/<version>/<installation-id>/` for environments, `current.json` for the validated active environment, `receipts/` for ownership and explicit registered targets, and `bin/` for stable launchers. On Linux/macOS offer `~/.local/bin` launchers only after checking ownership; on Windows use the application `bin` directory. Print the full usable executable path and PATH instructions. Do not silently edit shell profiles, the registry or execution policy. Running the virtual environment's interpreter by absolute path avoids requiring activation, as described by [Python's venv documentation](https://docs.python.org/3/library/venv.html).

Install only the verified local wheel, using the selected environment's Python and pip with `--isolated --no-index --no-deps`; this keeps the base installation independent of package indexes and optional SDK downloads. See the [pip install reference](https://pip.pypa.io/en/stable/cli/pip_install/). Release hashes check integrity relative to the trusted HTTPS release; they are not a claim of independent publisher authentication or signed artifacts.

## Review focus

1. A correct installed adapter may still resolve the wrong project when run from another directory. Test session, scaffold, infrastructure and docs guard with explicit entry context and without a helpful PYTHONPATH.
2. Generated inputs may change after preflight even though no physical adapter source exists. Detect mapping/renderer/bootstrap drift before writes, including when generated bytes happen to remain equal.
3. The same module has different destinations in registered and initialized runtimes. Preserve the frozen destination sets and avoid collisions or two independent writers for the five project helpers.
4. Custom, symlinked or incomplete source/runtime trees must remain protected across generated and file-backed assets, repeated upgrades and injected write failures.
5. Source tests can pass while wheel or source-distribution installation fails. Build both, rebuild a wheel from the source distribution, inspect contents and run outside the checkout without the optional SDK.
6. Installation may succeed while hooks use the wrong Python or shell on Windows. Test owned hooks, observer and statusline commands under the actual supported invocation forms, including paths with spaces and no `python3` alias.
7. Network errors, corrupt release assets or an interrupted/concurrent update must not replace a working installation. Validate inputs before activation and retain recovery receipts and referenced environments.
8. A clean uninstall must not remove edited assets, project documents, other tools or an interpreter still referenced by another registered project. Prove ownership and reference checks before deletion.
